# 推荐流式化设计

- 日期：2026-09-19
- 状态：已实现并用真实数据验证
- 前置：`2026-09-19-recommend-layer-design.md`、`2026-09-19-refine-and-group-design.md`

## 1. 问题

一次 `initial` 推荐要跑：LLM 调用 + 逆地理编码 + 每个地点一次高德地理编码。
实测应用层总耗时 **35 秒**，而用户全程只看到一句静态的「正在处理…」。

分阶段实测（真实提示词 + 真实输入）：

| 阶段 | 耗时 | 占比 |
| --- | --- | --- |
| 首个推理 token | 0.7s | — |
| 推理阶段 | 5.8s | 40% |
| **写 JSON** | **8.1s** | **60%** |
| LLM 小计 | 14.6s | |
| 高德核实（4 个请求，串行） | 约 20s | |

**真正的浪费不是「结果一次性出现」，而是两段时间没有重叠** —— LLM 写完 8 秒的 JSON
之后，核实才串行开始；而每个地点在它自己的对象写完时就已经可以拿去核实了。

## 2. 设计

```
DeepSeek 流 ──► 增量提取「已完整的地点对象」──► 立刻高德核实 ──► 推给客户端
```

服务端 `/api/recommend` 改返回 **NDJSON**（一行一个事件）：

| 事件 | 含义 |
| --- | --- |
| `stage` | `thinking` / `generating`，用于前端显示真实阶段 |
| `place` | 一个**已核实完**的地点，客户端立刻渲染成卡片 |
| `skipped` | 单条不合法被跳过（不是整次失败） |
| `done` | 收尾，带 `excluded` 与 `meta` |
| `error` | 失败原因 |

### 实测效果

| | 改之前 | 改之后 |
| --- | --- | --- |
| 第一张卡 | 35s | **17s** |
| 全部完成 | 35s | **22s** |

## 3. 三条关键决定

### 3.1 推理内容不展示给用户

模型 delta 里有 `reasoning_content`（这个模型是推理模型，会先输出很长的内部独白）。
**刻意不往下传内容，只传一个不带内容的「开始思考」信号** —— 内部独白展示给用户
既难懂又容易误导，而前端只需要知道「它在思考，不是卡住了」，这样 1 秒内就能给出真实反馈。

### 3.2 单条不合法只跳过那一条

非流式时「一条缺字段就全部作废」还说得过去；流式下已经推出去的东西，
为一条坏数据丢掉全部更糟。跳过的会记为 `skipped` 事件并告知用户。

### 3.3 中途断流保留已生成的部分

与「地理编码查不到的地点也保留」同一条原则：**不因为我们的网络问题抹掉模型已经
产出的真实结果**。界面上标黄说明「生成中断，下面可能不完整」+ 重试。

## 4. 增量 JSON 提取（`lib/recommend/array-item-stream.ts`）

从**流式到来的、尚未闭合的** JSON 里，逐个切出数组中已完整的对象。

不引依赖，手写约 80 行。核心测试是**在文本的每一个字符位置切开，提取结果必须完全一致**
（约 100 个断言）—— 流式最经典的 bug 就是「把 chunk 当成完整片段」，
一遇到跨 chunk 的字符串或转义就错。另有针对真实陷阱的用例：
字符串里的 `{}` 不能骗过括号配对、转义引号不能中断字符串、嵌套对象与数组、同名 key 只认第一个数组。

## 5. 范围

**只对 `initial` / `finalize` 上流式。** `refine` 返回的是 diff、通常只有 1~2 条，
流式没有收益，保持一次性返回。所以是两条路径并存。

## 6. 不做的两件事

| 项 | 为什么不 |
| --- | --- |
| 迁到 v5 `place/around` 取营业状态 | 实测同条件下 v3 与 v5 的有效填充率**都是 76%**，迁移零收益。详见 `2026-09-19-refine-and-group-design.md` 第 7.1 节 |
| 可选字段恒定化 + JSON Schema | 唯一消费者是 `parseSkillOutput` 与 UI，都已处理缺失；恒定化会让模型每次多吐一堆 `null`，白花 token 且增大出错面；契约文档已经存在，再加一份只会各自漂移。真需要时（对外提供 API）再做 |
