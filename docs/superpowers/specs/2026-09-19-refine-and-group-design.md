# 推荐层迭代设计：追问、细化、分组

- 日期：2026-09-19
- 状态：已与用户确认，待写实现计划
- 前置文档：`2026-09-19-recommend-layer-design.md`（本文件在其基础上扩展，不取代它）

## 1. 本轮要加什么

第一版是**单向**的：填偏好 → 出推荐 → 勾选 → 规划路线。用户没有反馈渠道，
只能在一批结果里挑，不满意就重来。

本轮把这条线变成可迭代的，并解决一个被忽略的粒度问题：

1. **自由输入**：第一个页面除预设标签外，再给一个输入框，用户可以自己说需求
2. **追问**：对单个地点追问（「我想在这吃点东西」）或对整批追问（「增加点能观光的地方」）
3. **细化**：把用户选中的**复合地点**拆成可导航的具体站点
4. **分组显示**：细化后保留父级作为分组标题
5. **二次勾选**：细化会新增点位，必须再给用户一次取舍机会，不能替他决定

## 2. 为什么「细化」这一步非有不可

初次推荐的地点可以是**复合的**——一个区域包含多个可玩点：

```
集美学村（龙舟池 + 集美大社 + 嘉庚建筑群）
```

**高德地理编码「集美学村」只能返回一个区域中心点。** 拿这个点去规划路线，
等于告诉导航「我要去集美学村」，但实际动线是先到龙舟池、再走到大社、再看建筑群。
这三个点各有坐标，**只有拆开才能逐段规划**。

所以细化不是「写得更详细」，它是路径规划的前置条件。也解释了为什么它排在选完之后：
用户先按**区域粒度**做取舍（集美学村值不值得去），定下来再按**站点粒度**排路线。

## 3. 完整流程

```
1. 用户进平台
2. 选出发点（定位 / 地图选点）
3. 填偏好：预设标签 + 自由输入框，点「帮我推荐」
4. 服务端逆地理编码得到「位置名 + 城市」
5. skill 初次推荐 —— 只给名称、地址、理由、contains，不给坐标
6. 高德逐条地理编码核实
     ├ 查得到 → 可上图、可勾选、可进路线
     └ 查不到 → 标「高德未能核实」，留在列表，不占编号、不可勾选
7. 地点显示；用户可勾选
     ├ 7.1 对单个地点追问（「我想在这吃点东西」）
     └ 7.2 对整批追问（「增加点能观光的地方」）
          └ 两者同一条路：skill 返回 added/removed + answer，平台按 diff 应用
8. 用户确认后，把选中的交给 skill 做「细化」
     └ 复合地点拆成子点（带 parent），单一地点原样透传
9. 细化结果重新渲染（父级作为分组标题），用户**再勾选一次**
10. 高德逐段路径规划（顺序由平台穷举优化）
11. 地图画折线，按拜访顺序统一编号；点开看详情
```

## 4. skill 契约

skill 需要支持三种任务，靠输入里的 `task` 区分。

### 4.1 输入

```jsonc
// 初次推荐
{
  "task": "initial",
  "origin": { "name": "厦门市集美区", "city": "厦门", "lng": 118.1, "lat": 24.6, "coordSystem": "GCJ-02" },
  "destination": { "mode": "nearby", "requested": null },
  "preferences": {
    "intents": ["拍照", "放松"], "timeBudget": "半天", "travelMode": ["步行"],
    "companions": 4, "crowdTolerance": "medium",
    "rawRequest": "想找个能坐下来的地方"        // 新增：输入框的自由文本，可为空
  }
}

// 追问（7.1 与 7.2 共用；scope 决定作用域）
{
  "task": "refine",
  "scope": "one",                              // "one" | "all"
  "origin": { ... },
  "preferences": { ... },
  "focus": { "name": "杨梅竹斜街", "address": "...", "category": "..." },  // scope=one 时给
  "previous": [ { "name": "...", "tier": "...", "category": "..." } ],     // scope=all 时给
  "followup": "我想在这吃点东西"
}

// 细化
{
  "task": "finalize",
  "origin": { ... },
  "preferences": { ... },
  "selected": [
    { "name": "集美学村", "contains": ["龙舟池", "集美大社", "嘉庚建筑群"], "address": "..." },
    { "name": "园博园", "address": "..." }
  ]
}
```

### 4.2 输出

**`initial` 与 `finalize` 输出形状相同**（`places` + `excluded` + `meta`），
所以平台能复用同一套渲染与核实流程。

```jsonc
// initial
{
  "places": [
    {
      "name": "集美学村",
      "category": "历史街区",
      "address": "厦门市集美区集美学村",
      "contains": ["龙舟池", "集美大社", "嘉庚建筑群"],   // 新增：复合地点才有
      "fit": [{ "tag": "拍照", "why": "..." }],
      "amap_url": "https://uri.amap.com/search?...",
      ...
    }
  ],
  "excluded": [...],
  "meta": { "assumptions": [...], "unverified": [...], "disclaimer": "..." }
}

// finalize —— 形状同上，但每个点更细，且有 parent
{
  "places": [
    { "name": "龙舟池", "parent": "集美学村", "address": "...", "fit": [...], "amap_url": "..." },
    { "name": "集美大社", "parent": "集美学村", ... },
    { "name": "嘉庚建筑群", "parent": "集美学村", ... },
    { "name": "园博园", "parent": null, ... }            // 单一地点原样透传
  ],
  "excluded": [{ "name": "某点", "reason": "半天时间不够，动线冲突" }],
  "meta": { ... }
}
```

**`refine` 输出是 diff，不是新列表**：

```jsonc
{
  "answer": "杨梅竹斜街东口往南 200 米有几家老字号，其中 X 家适合坐下来吃。",  // 回答用户的追问
  "added":   [ { 与 recommendations 同形状的推荐 } ],
  "removed": [ { "name": "大栅栏商业街", "reason": "人流密集，与你说的『想坐下来』冲突" } ]
}
```

**为什么追问用 diff 而不是整批替换**：整批替换会让用户已经认可的推荐无缘无故
消失或改名，用户会以为系统抽风。diff 让变化**可见、可解释**，也保留了用户的决策。

**diff 与用户当前选择的交互**（必须写死，否则会出现「选中的东西还在选中，但已经不在列表里」）：

- `added` 里的地点**默认不选中**——用户没要求过它
- `removed` 里的地点若当前处于选中状态，**自动取消选中**，并从路线里移除
- `removed` 必须给出 `reason`，在折叠区展示；不能悄悄消失

### 4.2.1 子点的增删怎么表达（2026-09-19 实测补充）

实测发现**「删掉一个子点」原本没有表达通道**：用户对「集美学村（龙舟池、集美大社）」说
「不想去龙舟池」，而契约禁止 `refine` 返回 `contains`，skill 只能把这件事写在 `answer` 里，
改不掉列表。同时 `added` 是纯追加，即使 skill 返回一个更新过的同名父级也只会变成重复项。

两条规则补上这个通道，由 `lib/recommend/apply-diff.ts` 实现：

1. **`added` 按名字 upsert**：同名命中 → **原地替换**（位置不变），新名才追加到末尾。
   所以 `refine` **可以且应当**返回一个 `contains` 已更新的同名复合地点。

   ```jsonc
   // 用户说「不想去龙舟池」
   "added": [
     { "name": "集美学村", "contains": ["集美大社", "嘉庚建筑群"], ... }
   ]
   ```

   这条顺带堵住了「同一个地点被推两遍」的重复项问题。

2. **`removed` 先匹配顶层、再匹配子点**：名字匹配不到任何顶层地点时，
   视为要剔除某个复合地点的子点，从它的 `contains` 里删掉。

   ```jsonc
   "removed": [{ "name": "龙舟池", "reason": "用户不想去，且环池与后续动线重复" }]
   ```

   两种写法平台都支持，skill 选其一即可；**但不要两个都写**（会重复表达同一件事）。

### 4.3 必须保持不变的不变量

写新提示词时这四条必须继续成立，否则平台会判失败或出安全问题：

1. `amap_url` 必须是 `https` + `amap.com` 或其子域（防提示词注入到 XSS）
2. `fit` 里同一个 `tag` 只能出现一条（多条证据合并进同一条 `why`）
3. **不给坐标、不给距离**（坐标由高德核实拿，距离由高德算）
4. 每条必须有 `name` 和 `amap_url`

## 5. 数据模型变更

```ts
// RecommendPlace 新增
contains?: string[]        // 复合地点包含的子点；单一地点不填
parent?: string | null     // 细化后：属于哪个复合地点；null 表示本身就是单一地点

// 新增
export type RefineResult = {
  answer: string
  added: RecommendPlace[]
  removed: { name: string; reason: string }[]
}
```

## 6. 界面变更

| 区域 | 变化 |
| --- | --- |
| 第一个页面 | 预设标签之外增加输入框（两者并存，都传给 skill） |
| 卡片 | 复合地点显示「含 N 个可玩点，细化后会拆开」的提示 |
| 卡片操作 | 新增「追问」入口（单个地点） |
| 列表顶部 | 新增「对这批不满意？」入口（整批追问） |
| 追问结果 | `added` 变成新卡片插入；`removed` 移除并在折叠区说明原因；`answer` 显示在提示条 |
| 细化后 | 按 `parent` 分组：父级作分组标题，子点缩进列在下面 |
| 细化后 | **重新变为可勾选状态**，用户再确认一次 |

**细化后的默认选中状态**（同样必须写死）：

粒度变了，原来的选择无法直接映射。规则是 —— **子点继承父级的选中状态**：

- 用户选了「集美学村」→ 它的子点（龙舟池 / 集美大社 / 嘉庚建筑群）**默认全部选中**
- 用户没选的父级，其子点默认不选
- skill 在细化时**新增**、且不属于任何已选父级的点，**默认不选**

这样用户的意图（「我要去集美学村」）不会因为拆解而丢失，而任务的重点变成
**让他取消掉不想要的子点**，而不是逼他重新选一遍。新增的点则必须由他主动勾选。

## 7. 高德核实与路线的影响

- 核实流程**不变**：仍然是对每个地点做地理编码 + 距离 + 营业状态
- **追问新增的地点也要走核实**——它可能来自模型的自由发挥，同样要用地理编码筛一遍
- **细化后的子点各自独立核实**（这正是不拆开就没法规划路线的原因）
- 路线规划不变，仍由平台穷举优化拜访顺序

### 7.1 实测结论：不迁到 v5 的 place/around（2026-09-19）

营业状态目前走 v3 的 `biz_ext.open_time`。曾怀疑该字段结构不稳（实测确实返回过数组，
是当初整个周边搜索 502 的元凶），考虑迁到 v5 的 `business.opentime_today`。

**在同一地点、同半径 2km、同取 25 条下实测对比：**

| 接口 | 有效填充 |
| --- | --- |
| v3 `biz_ext.open_time` | 19 / 25 = **76%** |
| v5 `business.opentime_today` | 19 / 25 = **76%** |

**两者完全一致**，迁移没有收益，只会带来改端点、改响应形状、重测的成本。

另外确认了那个 `[]` 的性质：v3 的 6 个空值**全部是空数组 `[]`**，即「没有值」的哨兵，
`asText([]) → ''` 已正确处理。v3 的 502 根因就此闭环。

**结论：不迁移。** 除非将来实测出 v5 有别的优势，否则不必再查。

## 8. 保持不变的原则

- skill 是唯一推荐来源，高德只做核实与路径，两者不合并
- 推荐失败直接显示「推荐失败」+ 重试，不做静默降级或后备入口
- 高德核实不到的地点保留在列表，标注「高德未能核实」，不占编号、不可勾选
- 距离一律是**直线距离**，界面必须标明
- 任何 `catch` 都不许静默吞错，必须留痕

## 9. 依赖

skill 提示词需要迭代以支持三种任务。提示词由用户提供，平台侧需要的是：

1. 提示词里体现 `task` 的分支（`initial` / `refine` / `finalize`）
2. `refine` 必须输出 `answer` + `added` + `removed` 的 diff 形状
3. `finalize` 必须输出带 `parent` 的细粒度地点，单一地点透传
4. 继续遵守第 4.3 节的四条不变量
